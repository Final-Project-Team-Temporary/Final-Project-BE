# AI 협업 가이드 — Claude Code에게 작업 지시하는 법

> 이 프로젝트는 하네스 프로그래밍 방식을 적용했다. 에이전트(Claude Code)는 세션마다 루트 `CLAUDE.md`를 먼저 읽고, 작업 디렉터리에 따라 경로별 `CLAUDE.md`를 추가로 읽으며, `.claude/commands/`의 슬래시 커맨드와 `.claude/settings.json`의 권한 정책을 따른다.
> 이 문서는 **사람(개발자)** 이 어떻게 지시해야 에이전트가 가장 잘 동작하는지에 대한 가이드다.

## 한 줄 요약

> **"무엇을 / 왜 / 어디에 / 어떻게 검증할지"** 를 담아라. 그러면 에이전트는 Plan→Work→Verify 루프로 알아서 끝낸다.

---

## 1. 좋은 지시의 4요소

| 요소 | 빠지면 생기는 일 | 예시 |
|------|------------------|------|
| **무엇(What)** | 엉뚱한 걸 만든다 | "퀴즈 즐겨찾기 기능 추가" |
| **왜/맥락(Why)** | 과·소설계한다 | "사용자가 어려웠던 용어를 다시 풀 수 있게" |
| **어디(Where)** | 엉뚱한 모듈을 건드린다 | "`quiz` 도메인에" |
| **검증(Done)** | 동작 보장이 안 된다 | "단위 테스트 추가하고 `./gradlew test` 통과" |

네 가지를 다 적을 필요는 없다. 하지만 **클수록 다 적어라.** 작은 수정은 "무엇"만으로 충분하다.

---

## 2. 작업 크기별 추천 패턴

### 작은 수정 (버그·문구·단순 변경)
바로 지시한다.
```
QuizController의 getQuiz에서 term이 빈 문자열일 때 NPE 나는 거 고쳐줘
```

### 중간 기능 (엔드포인트 1~2개 추가)
슬래시 커맨드를 쓴다.
```
/feature 사용자가 푼 퀴즈를 즐겨찾기에 추가/조회/삭제하는 API. quiz 도메인에, 로그인 사용자 기준.
```
→ 에이전트가 영향 범위·DTO·ErrorStatus를 먼저 제시하고, 구현 후 컴파일·테스트까지 돈다.

### 큰 기능 / 새 도메인
**계획부터 받는다.** 먼저 계획만 요청하고, 확인 후 구현시킨다.
```
모의투자에 '관심종목(watchlist)' 기능을 추가하려고 해. 바로 짜지 말고
먼저 어떤 파일·엔드포인트·엔티티가 필요한지 계획만 세워줘.
```
계획이 괜찮으면:
```
좋아, 그대로 구현해줘. 새 도메인이면 /new-domain watchlist 로 골격부터.
```

### 변경 점검
커밋 전에 셀프 리뷰를 돌린다.
```
/review-diff
```

## 3. 실전 예시 — Before / After

**❌ 모호한 지시**
> 퀴즈 좀 개선해줘

**✅ 좋은 지시**
> `quiz` 도메인에서, 사용자가 **틀린 문제만 다시 푸는** 복습 모드를 추가하고 싶어.
> - 기존 `QuizSolveLog`(log 도메인)에서 오답을 가져와 구성
> - 엔드포인트: `GET /api/quiz/review`
> - 로그인 사용자 기준, 응답은 기존 `QuizResDto` 재사용 가능하면 재사용
> - 서비스 단위 테스트 추가하고 `./gradlew test --tests "*Quiz*"` 통과 확인
> 먼저 변경 범위부터 알려주고 진행해줘.

차이: 도메인·데이터 출처·엔드포인트·검증 기준·"계획 먼저"가 모두 명시됨.

## 4. 에이전트를 잘 쓰는 습관

- **추측 금지를 유도하라**: "모르면 묻고 진행해줘"를 붙이면 잘못된 가정을 줄인다.
- **검증을 항상 요구하라**: "테스트 통과까지 확인해줘". 이 프로젝트는 통합 테스트에 **Docker가 필요**하니, 환경이 없으면 "컴파일(`compileJava`)까지만 확인"으로 낮춰 지시한다.
- **컨벤션은 다시 설명하지 마라**: `ApiResponse`·`WhiplashException`·DTO 네이밍 등은 `CLAUDE.md`에 있다. 반복 설명 대신 "컨벤션대로"라고만.
- **커밋/푸시는 명시적으로**: 에이전트는 시키기 전엔 커밋·푸시·PR을 하지 않는다. 필요할 때 "feature 브랜치 만들어 커밋해줘"처럼 직접 지시.
- **컨텍스트가 길어지면 분리하라**: 서로 다른 기능은 새 세션/대화로. 한 작업이 끝나면 `/review-diff`로 마무리.
- **큰 작업은 단계로 끊어라**: "계획 → (확인) → 구현 → (확인) → 테스트". 한 번에 다 시키기보다 체크포인트를 둔다.

## 5. 하네스 구성 자산 (유지보수)

| 파일 | 역할 | 갱신 시점 |
|------|------|-----------|
| `CLAUDE.md` (루트) | 프로젝트 지도·컨벤션·절대 규칙 | 구조/규약이 바뀔 때 |
| `src/test/.../CLAUDE.md` | 테스트 작성 규약 | 테스트 베이스 클래스가 바뀔 때 |
| `.claude/settings.json` | 팀 공유 권한 정책(허용/거부 명령) | 자주 쓰는 안전 명령이 늘 때 |
| `.claude/commands/*.md` | 표준 작업 슬래시 커맨드 | 반복 작업 패턴이 생길 때 |
| `.claude/settings.local.json` | **개인** 설정(비공유, gitignore) | 각자 자유 |

> 핵심 원칙: **컨벤션이 바뀌면 코드보다 `CLAUDE.md`를 먼저 고친다.** 그래야 에이전트가 계속 올바른 패턴으로 코드를 생성한다.
